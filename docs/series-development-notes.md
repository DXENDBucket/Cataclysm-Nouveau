# Boss 系列的完成边界与审计经验

截至 dev.7，下界合金巨兽系列可以阶段性收尾。主要攻击、熔岩炸弹、吸收、肩撞及相关状态已接入；不以复制全部 Boss AI 为完成标准。震退被用户明确放弃，拆方块和 Boss 防护规则未接入。客户端待验证项继续保留，不能因进入下个系列而写成已验证。

## 整套能力的获取原则

用户明确：后续灾变 Boss 通常击杀 **1–3 次即可获得全部能力**。默认按单名玩家制作并学习每种魔符各一次计算；多人分别学习、补做重复魔符的额外消耗另计。

- 先汇总整套配方需要的 Boss 材料，再与实际发布 JAR 的掉落表对照。间接制作材料所需的 Boss 掉落也算入总量，不能只看每个魔符的独立配方。
- 少量核心、综合强度高的能力使用数量少的标志性掉落；其他能力优先采用数量较多的掉落。物品能力适合时可以使用对应 Boss 武器。图标与配方材料可独立选择。
- 判断随机掉落时考虑通常获得的数量与概率，避免低概率素材成为学齐整套的隐性长期刷取门槛。新增能力后重新核对总需求。
- 魔源宝石、经验等正常制作成本可以保留。原生 Boss 掉落不需为每个新增魔符改动；材料分配优先服务整套获取目标。

dev.10 巨兽示例：两种犄角配方、一种锻锤配方、七种电池配方。原生每次掉一个犄角、一个锻锤和 16–24 个电池，因此两次击杀足够制作整套十种能力，且还可保留一把锻锤使用。

## 新 agent 必须获得的判断依据

- 原模组完整实现优先于只复刻一次伤害。查服务端入口，同时查同步、实体事件、渲染器、粒子、声音、命中后子效果与结束过程。
- 同类能力优先 Boss 版本；没有物品施法来源时可以采用 Boss 直接掉落物制作。不要机械地把只适合 Boss 身体的动作、防护或地形破坏全部做成魔符。
- 区分施法者、执行者、受益目标和付款者。友军执行冲锋并不意味着由友军支付；所有者/伤害归属用 Core 上下文，友军用 Core API。
- 原生轨迹和 Ars 轨迹只保留一个运动驱动者。普通、持续/重复载荷分别检查命中次数、费用和接续次数；子攻击属于已付费用时不要再次收费，也不要各自复制整段 Ars 后续效果。
- 临时修改世界必须覆盖自然结束、所有者离开、区块卸载、重启及位置被替换；不能只在实体正常死亡时清理。
- 新状态能力说明清楚默认时长、修饰公式、上限和保护范围。不要给共享形态写某一种载荷专用的增强说明。
- 图标父模型可能是 builtin/entity，必须检查真实物品身份和原生渲染入口。文本要核对 Ars 实际使用的 glyph_name 与增强说明键。
- 费用结合命中覆盖、持续攻击、控制及组合能力评估；Iron 的对照等级不能始终假定为 1。参考相邻 Ars-Balance-Baselines 的当前记录，尚未实际测到的数据应标为估算。
- 收拢修改后做必要验证。GameTest 不能证明客户端画面完整；既有成功记录不能替代新代码的检查。固定 Core 副本不改，公共修复另开明确的 Core 任务。

## dev.14 动作核对经验

把 Boss 动作转成友军增益时，付款者、伤害拥有者与运动执行者应分开；需要按实际执行者阻止重复动作。原生内部攻击方法可能直接构造 mobAttack(Boss)，即使子实体已重绑 owner，近战仍需单独改归属。旋风原生推力不自动排除友军，需要 opt-in 过滤，不能改变本体 Boss 的规则。

多目标 Mixin 的 @Shadow 需要显式 remap=false；类级 remap=false 不能替代此处的核对。GameTest 计数必须区分主攻击和火花落地等子攻击；同一落地雷暴有 35 道主落雷，不能把两枚火花产生的落雷视为额外重复执行。瞬态 Boss 的服务器帧不会自动产生客户端粒子，仍要显式发送原生资源。

## dev.20：组合攻击与数值修饰

完整原生goal可能包含多次齐射，必须逐一核对发射tick及每次数量；先驱者榴弹是两轮5/7，不是总量5/7。脱离世界的Boss调用帧需要校准炮口高度，所有子实体重绑真实伤害拥有者，并有自己的生命周期；子攻击不自动重复收费或执行后续编排。脱离世界的Boss不能广播自己的动画ID，可捕获原生动画请求安排连续动作。

用户最终采用伤害增强步长 `min(10,max(2,0.20*D_base))`。需要保留原生基础字段，另存修饰倍率；否则百分比封顶和子实体很容易重复吃增强。服务端伤害拦截覆盖实际覆写hurt调用的具体弹体类，而不只抽象父类；数值状态放在共同父类一次，避免多级Mixin各存一份。此次验证发现水矛具体类单独定义了命中伤害，需要补拦截。配置修改后的测试要核对隔离测试实例已保存的值，不能把旧配置值当新默认值。

## dev.21：烟云显示的再次处理

用户在dev.20仍看不到烟云，dev.19的noCulling仅证明了同步标记，不能当作客户端问题已解决。此次联动烟云每两tick通过原版粒子包发送一批SMOKE，位置抬高0.2格，不依赖客户端烟云实体tick；客户端原生粒子发射仅对联动实例抑制，避免双份。原生实体仍管理伤害、等待、半径和清理。批量包的分布与本体逐粒子圆盘采样略有区别；采用这条可验证的传输路径不等于确认了旧路径失败的具体原因。新增检查须捕获实际发给附近玩家的粒子包，而非只判断烟云实体存在；客户端画面需单独确认。

## dev.23：末影守卫首批

四项已实现：守卫炮弹、虚空漩涡、完整践踏符文阵、引力重拳。炮弹准备期必须同时阻止原生伤害和Ars续接，特殊轨迹的原生到期移除也要抑制。漩涡的牵引/结束爆炸原生两端都执行，联动需保留客户端视觉但由服务器同步运动；结束爆炸的伤害源显式指定真实拥有者，因为漩涡不是Projectile，原版爆炸不能自动推断owner。伤害过滤不能替代牵引/挑起等物理过滤。践踏子符文应继承上下文并独立清理，原生RuneDamage9不能改读原有单符文魔符的默认7。

配方两只护手用于漩涡和重拳，两枚末影傀儡虚空核心用于炮弹与践踏；核心不是守卫掉落，获取预算明确区分。服务端56项检查通过，客户端外观未人工验证。Core保持固定0.1.19不改。
